§1 EXECUTIVE SUMMARY
================================================================================

libsandbox.1.dylib is the **Seatbelt profile compile/apply** library. It is
dlopen'd by libsystem_sandbox.dylib (sandbox_init_with_parameters) and directly
by Dopamine systemhook (sandbox_apply hook target).

Key findings for tvrootshell:

  1. **sandbox_apply** @ 0x18CF3F2F0 is an 8-byte wrapper:
       sandbox_apply(profile) → sandbox_apply_container(profile, NULL)

  2. **apply_container** calls kernel MIG:
       - routine **1** when profile->name (*profile != 0) — named profile path
       - routine **0** when profile->name is NULL — bytecode profile path
     This installs/updates the process **slot-0 Seatbelt profile** in kernel
     (532A80 / 532930 chain — see kernel study).

  3. **Userspace profile compilation is DISABLED on tvOS 16.5:**
       sandbox_compile_string, sandbox_compile_file, sandbox_compile_entitlements
       all return NULL and set error:
         "profile compilation not supported on this platform"
       Only **sandbox_compile_named** works — via kernel MIG **22** (0x16).

  4. **No extension APIs** in this dylib — extension issue/consume stays in
     libsystem_sandbox.dylib (MIG 5/6).

  5. **No mac_label / slot / unsandbox** anywhere (same as libsystem_sandbox).

  6. Dopamine **systemhook** hooks sandbox_apply via **dyld dlsym hook** (not
     instruction patch). After original apply, hook calls
     consume_tokenized_sandbox_extensions() using tokens from launchdhook checkin.

For build102.3.3: helper never gets sandbox_apply hook + never consumes extensions
into its live profile before spawning dash → op 16 deny unchanged.

│ libsystem_sandbox.dylib                                                  │
│   Extensions: issue (MIG 5), consume (MIG 6), check (MIG 2)              │

         │ dlopen("/usr/lib/libsandbox.1.dylib")
         ▼

│ libsandbox.1.dylib  ← THIS FILE                                          │

│   sandbox_apply → apply_container (MIG 0 or 1) → kernel slot-0 profile   │
└──────────────────────────────────────────────────────────────────────────┘
         │ __sandbox_ms("Sandbox", routine, args)
         ▼
┌──────────────────────────────────────────────────────────────────────────┐

└──────────────────────────────────────────────────────────────────────────┘

Dopamine adds systemhook between layers 2 and 3:
  sandbox_apply_hook → orig apply (MIG 0/1) → consume JB tokens (MIG 6)

§4 PROFILE OBJECT LAYOUT (24 bytes)
================================================================================

From sandbox_compile_named success path + sandbox_free_profile + apply_container:

  struct sandbox_profile {          // 0x18 bytes allocated
    char *primary;                  // +0x00 — profile name (named path)
    void *field8;                   // +0x08 — bytecode ptr (MIG 0 path)
    void *field10;                  // +0x10 — bytecode len/metadata (MIG 0 path)
  };

sandbox_compile_named(name, flags, errbuf):
  1. MIG 22 with &name — kernel validates named profile exists
  2. If MIG returns **0** (success): allocate 24 bytes, strdup(name) → primary
  3. If MIG returns **non-zero**: fall back to compile_file (always fails tvOS)

sandbox_apply_container(profile, container_path):
  if (profile->primary != NULL) {
    args = { profile->primary, container_path, strlen(container)+1 };
    __sandbox_ms("Sandbox", **1**, &args);     // NAMED APPLY
  } else {
    args = { profile->field8, profile->field10, container_path, strlen+1 };
    __sandbox_ms("Sandbox", **0**, &args);     // BYTECODE APPLY
  }

sandbox_apply(profile):
  return sandbox_apply_container(profile, NULL);   // container = 0

Disasm proof (apply_container @ 0x18CF3F260):
  CBZ [X0]           → branch to LDP [X0,#8] (bytecode path)
  MOV W1, #1         → named path MIG routine 1
  ...
  MOV W1, #0         → bytecode path MIG routine 0
  BL  __sandbox_ms

**tvOS implication:** TrollStore/container apps use **named profiles** (e.g.
"container") compiled in kernel via MIG 22, then applied via MIG 1. The MIG 0
bytecode path exists in code but userspace cannot produce bytecode on tvOS.

================================================================================
§5 tvOS — PROFILE COMPILATION DISABLED
================================================================================

All three userspace compile paths that read .sb files or raw strings fail:

  sandbox_compile_string @ 0x18CF3F1B8:
    snprintf(err, "profile compilation not supported on this platform")
    return NULL

  sandbox_compile_file @ 0x18CF3EFE8:
    Opens /System/Library/Sandbox/Profiles/<name>.sb or /usr/share/sandbox/
    On success opening file → same error message → fclose → return NULL
    (file open works; compilation step deliberately blocked)

  sandbox_compile_entitlements @ 0x18CF3F1F0:
    Same stub error → return NULL

Profile search paths (compile_file only, before fail):
  /System/Library/Sandbox/Profiles/%s.sb
  /usr/share/sandbox/%s.sb

**Only working compile:** sandbox_compile_named → kernel MIG **22** (0x16).
Kernel-side named profile lookup/validation; userspace gets back a profile
object with strdup'd name only (no local bytecode).

libsystem_sandbox sandbox_init_with_parameters flags mapping on tvOS:
  flags=0 (compile_string)  → **will fail** on tvOS
  flags=1 (compile_named)   → **works**
  flags=2 (direct MIG 1)    → bypasses libsandbox compile (libsystem_sandbox)
  flags=3 (compile_file)    → **will fail** on tvOS

================================================================================
§6 sandbox_apply — DOPAMINE systemhook HOOK TARGET
================================================================================

Dopamine systemhook (main.c):

  gLibSandboxHandle = dlopen("/usr/lib/libsandbox.1.dylib", ...);
  sandbox_apply_orig = dlsym(gLibSandboxHandle, "sandbox_apply");

  dyld_hook_routine(gDyld, 17, dyld_dlsym_hook, ...);
  // When libsystem_sandbox dlsym's "sandbox_apply", return sandbox_apply_hook

  void *sandbox_apply_hook(void *profile) {
    void *r = sandbox_apply_orig(profile);   // MIG 0/1 → kernel slot-0
    consume_tokenized_sandbox_extensions(JB_SandboxExtensions);
    return r;
  }

Hook timing:
  - Called when **child process** applies Seatbelt profile during spawn/container
    setup (after kernel has bound a profile object to the process cred).
  - consume runs **after** apply so extensions attach to the **live profile**
    that 532930 will read for op 16/129 checks.

Token source (JB_SandboxExtensions):
  - launchdhook systemwide_process_checkin issues read + read-write + executable
    extensions on /var/jb via sandbox_extension_issue_file_to_process
  - Pipe-separated tokens passed via dyldhook __jbinfo / jbclient_process_checkin
  - systemhook constructor may also consume at init (if dyldhook didn't)

tvrootshell gap:
  - No systemhook injection into helper or dash child
  - No launchdhook to issue per-process tokens
  - build97 manual consume in app context ≠ consume on helper's profile at spawn

§8 PARAMS OBJECT (sandbox_create_params / set_param)
================================================================================

sandbox_create_params @ 0x18CF3EE6C:
  Allocates 24-byte object:
    +0x00: pointer to key-value array (16-byte pairs: key ptr, value ptr)
    +0x08: count (number of pairs × 2 slots)
    +0x10: capacity (starts 0 from xmmword init)

sandbox_set_param(params, key, value):
  Linear search for existing key; append or update key/value pair.
  Used before compile/apply in sandbox_init_with_parameters path.

Not directly relevant to extension triple for /var/jb — params customize profile
variables at compile/apply time (container paths, etc.).

§9 INSPECT / DEBUG APIs
================================================================================

sandbox_inspect_pid(pid, flags, err, &out) → sb_inspect_subsystem(1, pid, ...)
  Loop up to 10 times with growing 4KB buffer; MIG 16 until success or errno≠63.
  Returns packed sandbox state blob (sb_packbuff format).

sandbox_inspect_smemory → stub return 45 (unsupported on tvOS).

Useful for **device diagnostics** on helper vs app profile contents (future BP
session complement).

§11 tvrootshell IMPLICATIONS (study only — no build)
================================================================================

WHAT THIS CLOSES:
  - sandbox_apply does NOT read mac_label slot 1 (confirms kernel + libsystem)
  - tvOS cannot compile custom .sb profiles in userspace
  - Dopamine hook point is exactly sandbox_apply @ 0x18CF3F2F0 (8 bytes)
  - Apply uses MIG 1 for container named profiles (TrollStore app path)

WHAT IS STILL REQUIRED FOR /var/jb dash:
  Option A (minimal, no systemhook port):
    In helper process after privesc, before posix_spawn(dash):
      sandbox_extension_issue_file × 3 (read, rw, executable on /var/jb)
      sandbox_extension_consume × 3 on **helper pid profile**
      verify handles != 0 (5510E8 gate)
    Child inherits profile via 533304 — extensions should carry if consumed
    into parent profile before fork/spawn.

  Option B (Dopamine-full):
    systemhook sandbox_apply_hook + launchdhook token issue — needs inject
    infrastructure (Layer 4/6 — high scope on tvOS).

WHAT NOT TO DO:
  - Hook sandbox_apply without consume — apply alone doesn't grant /var/jb
  - Rely on sandbox_compile_string/file on tvOS — hard-disabled
  - Expect sandbox_register_profile (stub 45) to help

OPEN (device/kernel):
  - Confirm MIG 1 handler = 532A80 with helper pid at consume time
  - build99 O1: 532C68 NULL at 5510E8 — which proc cred?
  - Does persona-spawned helper share app cr_label?
